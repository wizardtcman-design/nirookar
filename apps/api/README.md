# apps/api — Backend آینده (فعلاً فقط ساختار و مرز معماری)

> ⚠️ **این بخش در فاز ۱ عملیاتی نیست.** طبق دستور مالک پروژه، بدون تأیید جداگانه
> هیچ Backend عملیاتی، احراز هویت واقعی یا اتصال پایگاه داده ساخته نمی‌شود.
> این پوشه فقط «جایگاه و مرزهای آینده» را در معماری ثبت می‌کند تا بعداً
> بدون بازنویسی UI به پروژه اضافه شود.

## فناوری پیشنهادی (فقط گزینه — نیازمند تأیید)

- **Node.js + TypeScript**
- **NestJS** به‌عنوان گزینه معماری بررسی شود (تأیید نشده)
- **PostgreSQL** به‌عنوان گزینه اصلی پایگاه داده بررسی شود (تأیید نشده)

## مرزهای ماژول‌های آینده

هر پوشه در `src/modules/` نمایانگر یک Bounded Context آینده است:

| ماژول | مسئولیت آینده |
|---|---|
| `auth` | احراز هویت، ثبت‌نام، توکن‌ها، بازیابی رمز |
| `users` | پروفایل مشتریان، فعال/غیرفعال/مسدودسازی با Audit Log |
| `shops` | مدارک و احراز صلاحیت فروشگاه‌ها، محصولات و خدمات |
| `installers` | مهارت‌ها، سفارش‌های دریافتی، امتیاز و تخلفات نصاب‌ها |
| `orders` | ثبت سفارش، واگذاری، **پیگیری زنده با تاریخچه Append-Only تغییر وضعیت** |
| `finance` | کمیسیون‌ها، تسویه‌حساب، گزارش درآمد روزانه/ماهانه/سالانه |
| `violations` | ثبت شکایت، رسیدگی، جبران خسارت، ضمانت اجرا |
| `reports` | آمار و گزارش‌های قابل فیلتر پلتفرم |
| `settings` | تنظیمات عمومی، نقش‌ها، شهرها، دسته‌بندی خدمات، اطلاع‌رسانی |

## قواعد اتصال (از روز اول در معماری لحاظ شده)

1. UI هرگز مستقیماً به Backend وابسته نیست؛ فقط به **قراردادهای
   Service/Repository** (`src/services/contracts` در وب + `packages/shared`).
2. برای اتصال، فقط پیاده‌سازی Repository عوض می‌شود
   (مثال موجود: `UnimplementedAuthRepository` → `RestAuthRepository`).
3. کنترل دسترسی پنل مدیریت (RBAC) باید **سمت سرور** اجرا شود — مدل مجوزها
   از قبل در `packages/shared/src/admin-rbac.ts` تعریف شده است.
4. هر عملیات حساس باید در Audit Log ثبت شود (شخص، زمان، قبل/بعد).
5. هیچ Secret یا کلیدی در کد قرار نمی‌گیرد؛ همه از متغیرهای محیطی/Secrets.
