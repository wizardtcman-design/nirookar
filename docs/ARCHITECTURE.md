# معماری پلتفرم نیروکار

نسخه: فاز ۲ گام ۱ — احراز هویت واقعی (OTP Sandbox)، API Routes + SQLite، تنظیمات پویا

---

## ۱) دید کلی — سه محصول مستقل اما هماهنگ

```
nirookar/
├── src/                     ← وب‌سایت + پنل مدیریت (Next.js 16, React, TS) + API Routes + لایه سرور
│   ├── app/api/             ← API واقعی: auth، auth/register، admin/*، platform/config
│   ├── server/              ← seed، نشست (کوکی امن)، Audit Log، گارد RBAC سمت سرور
│   ├── components/          ← نماها (nirookar) + پنل مدیریت (admin)
│   ├── services/            ← قرارداد Repository + پیاده‌سازی واقعی HttpAuthRepository
│   └── lib/                 ← نقش‌ها، اعتبارسنجی (re-export از shared)، نسخه، ناوبری
├── apps/
│   ├── mobile/              ← اپ موبایل (Expo + React Native + TypeScript)
│   └── api/                 ← مرز ماژول‌های Backend آینده (غیرعملیاتی — جایگاه معماری)
├── packages/
│   ├── shared/              ← نقش‌ها، RBAC، اعتبارسنجی (کد ملی/شبا)، PlatformSettings، ماتریس امکانات، نسخه
│   └── config/              ← تنظیمات مشترک (tsconfig پایه، الگوی env)
├── prisma/ + db/            ← اسکیمای SQLite (User، پروفایل‌ها، Session، OtpCode، PlatformSettings، AuditLog)
└── docs/                    ← معماری، ماتریس امکانات، نقشه راه، نسخه‌بندی
```

**تصمیم مالک:** وب در ریشه مخزن (`src/`) می‌ماند تا پیش‌نمایش زنده بدون اختلال کار کند؛
انتقال به `apps/web` بسته شد. میراث Flutter (`flutter_app/`) طبق تأیید مالک حذف شد و
معماری قطعی موبایل **Expo + React Native** است.

## ۲) لایه‌های نرم‌افزار

```
UI (View Components)
   │  فقط فراخوانی قراردادها — هیچ منطق تجاری
   ▼
Service / Repository Contracts   (src/services/contracts + packages/shared)
   │  UI به «قرارداد» وابسته است نه پیاده‌سازی
   ▼
Repository Implementations
   ├── فاز ۱: Unimplemented (حذف شد — جایگزین با پیاده‌سازی واقعی)
   └── فاز ۲ گام ۱: HttpAuthRepository → API Routes → Prisma/SQLite
       (تعویض آینده به PostgreSQL = فقط تغییر datasource؛ صفر بازنویسی UI)
```

- **اصل وابستگی معکوس:** تعویض Backend = تعویض پیاده‌سازی Repository؛ صفر بازنویسی UI.
- **خطای صادقانه:** هیچ دکمه‌ای موفقیت جعلی نشان نمی‌دهد؛ قابلیت‌های فعال‌نشده
  وضعیت واقعی خود را اعلام می‌کنند و داده‌های نمایشی برچسب Demo دارند.

## ۲-۱) احراز هویت (فاز ۲ گام ۱)

- **جریان:** شماره موبایل → کد OTP (آزمایشی: `12345` — Sandbox) → ورود یا فرم ثبت‌نام نقش.
- **نشست:** کوکی `httpOnly` با توکن تصادفی ۳۲ بایتی (مدل `Session`)؛ هیچ رمز/توکنی در localStorage نیست.
- **OTP:** مدل `OtpCode` با انقضا ۲ دقیقه و مصرف یک‌باره — ساختار آماده اتصال سرویس پیامک واقعی است؛ در Sandbox کد ثابت آزمایشی است و صادقانه برچسب‌گذاری شده.
- **ثبت‌نام نصاب/فروشگاه:** وضعیت اولیه `PENDING_VERIFICATION`؛ فعال‌سازی فقط با تیک
  «تأیید قرارداد و دریافت سفته حضوری» توسط مدیر (Audit Log).
- **قفل کد ملی:** الگوریتم ریاضی در shared + Unique constraint در دیتابیس + هشدار ادمین (Audit) در تلاش تکراری.

## ۳) نقش‌ها و توسعه‌پذیری

- **منبع حقیقت نقش‌ها:** `packages/shared/src/roles-core.ts` (داده خالص) —
  وب و موبایل هرکدام ظاهر خودشان را روی همین داده سوار می‌کنند.
- افزودن نقش جدید (راننده وانت‌بار، شرکت حمل‌ونقل، متخصص تعمیرات) = افزودن یک
  entry + ظاهر پلتفرمی؛ بدون بازنویسی هیچ صفحه‌ای.
- نقش‌های آینده در `FUTURE_ROLES` ثبت شده‌اند ولی **هیچ UI ندارند**.
- دسته‌بندی خدمات از نقش‌ها جدا است؛ شهرهای فعال از تنظیمات پنل مدیریت تعریف
  می‌شود (بدون هاردکد شهر) و گسترش به حوزه‌های جدید در فازهای آینده انجام می‌شود.

## ۴) پنل مدیریت مرکزی

- **جایگاه:** وب مستقل و امن در کنار وب‌سایت؛ **هرگز** داخل اپ عمومی مشتری/نصاب/فروشگاه.
- **دسترسی (فاز ۲):** لینک عمومی در صفحه اصلی وجود ندارد؛ ورود واقعی با OTP و فقط
  با نقش‌های مدیریتی. برای کاربر لاگین‌شده با نقش مدیریتی، دکمه طلایی «اتاق فرمان /
  مدیریت» در هدر نمایش داده می‌شود. سوییچر سریع نمایشی (Demo) برای تست مالک حفظ شده.
- **RBAC دو لایه:** فیلتر منو در UI + گارد `requireAdmin` سمت سرور روی تمام مسیرهای
  `/api/admin/*` (پاسخ 401/403 واقعی) — ماتریس در `packages/shared/src/admin-rbac.ts`.
- **Audit Log واقعی:** ثبت‌نام، ورود، تأیید قرارداد و سفته، تغییر تنظیمات و تلاش کد ملی
  تکراری — Append-Only و فقط-خواندنی.
- **داده‌ها:** کاربران/نصاب‌ها/فروشگاه‌ها/داشبورد/تنظیمات = زنده از دیتابیس؛
  سفارش‌ها/مالی/شکایات/گزارش‌ها = هنوز نمایشی (برچسب Demo) تا ساخت سیستم سفارش.
- **تنظیمات پویا:** تمام اعداد تجاری از `PlatformSettings` — ویرایش زنده در پنل + ثبت تغییرات در Audit.

## ۵) ناوبری و مسیرها

کل تجربه وب روی مسیر «/» با ناوبری hash اجرا می‌شود (تصمیم مالک برای حفظ پیش‌نمایش زنده)،
پشتیبانی کامل از دکمه بازگشت مرورگر:

| مسیر | نما |
|---|---|
| `#/` | خانه و انتخاب نقش (بدون لینک عمومی ادمین) |
| `#/login/customer` | ورود/ثبت‌نام مشتری (OTP) |
| `#/login/installer` | ورود/ثبت‌نام نصاب (OTP + پرونده کامل) |
| `#/login/shop` | ورود/ثبت‌نام فروشگاه (OTP + پرونده کامل) |
| `#/guide` | راهنما |
| `#/about` | درباره ما |
| `#/status` | وضعیت توسعه + ماتریس امکانات |
| `#/admin` | پنل مدیریت (ورود واقعی OTP — فقط نقش‌های مدیریتی) |
| `#/admin/{overview,users,shops,installers,orders,finance,violations,reports,settings}` | بخش‌های پنل |

**مهاجرت به مسیرهای واقعی Next.js (آینده):** قرارداد ViewId در
`src/lib/navigation.ts` متمرکز است؛ انتقال به App Router شامل ساخت
`app/(routes)/...` و حذف لایه hash — بدون تغییر هیچ کامپوننت UI.

## ۹) امنیت در معماری

- قرارداد Repository → منطق تجاری به UI نشت نمی‌کند.
- هیچ Secret در کد/مخزن؛ `.env*` در gitignore؛ الگو: `packages/config/env.example`.
- نشست با کوکی httpOnly + توکن تصادفی؛ OTP مصرف‌شدنی با انقضا (در این فاز Sandbox).
- RBAC سمت سرور روی تمام `/api/admin/*` (گارد requireAdmin با ماتریس مجوزهای shared).
- Audit Log Append-Only برای عملیات حساس؛ هیچ مسیر ویرایش/حذف ندارد.
- آدرس سکونت نصاب محرمانه — فقط با مجوز «installers.view» از سرور ارسال می‌شود.
- ⚠️ محدودیت‌های شناخته‌شده این فاز: OTP آزمایشی (کد ثابت 12345)، تصاویر به‌صورت
  dataURL در دیتابیس (حد ~۶۰۰KB)، و حالت نمایشی ادمین (سوییچر سریع) که با env
  `NIROOKAR_DEMO_MODE=false` غیرفعال می‌شود. این موارد قبل از انتشار عمومی باید
  با سرویس پیامک واقعی، object storage و غیرفعال‌سازی Demo جایگزین شوند.
