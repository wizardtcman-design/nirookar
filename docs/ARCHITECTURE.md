# معماری پلتفرم نیروکار

نسخه: فاز ۱ — به‌روزرسانی پس از افزودن Monorepo، اپ موبایل Expo و پنل مدیریت

---

## ۱) دید کلی — سه محصول مستقل اما هماهنگ

```
nirookar/
├── src/                     ← وب‌سایت + پنل مدیریت (Next.js 16, React, TS)  = apps/web (نگاشت فعلی)
├── apps/
│   ├── mobile/              ← اپ موبایل (Expo + React Native + TypeScript)
│   └── api/                 ← Backend آینده — فقط ساختار و مرز ماژول‌ها (غیرعملیاتی)
├── packages/
│   ├── shared/              ← کد و داده مشترک: نقش‌ها، RBAC، اعتبارسنجی، ماتریس امکانات، نسخه
│   └── config/              ← تنظیمات مشترک (tsconfig پایه، الگوی env)
├── flutter_app/             ← ❄️ میراث مشخصات قبلی — منجمد؛ بدون توسعه (بخش ۶)
└── docs/                    ← مستندات معماری، ماتریس امکانات، نقشه راه، نسخه‌بندی
```

**نقشه‌برداری فعلی:** وب‌سایت فعلاً در ریشه مخزن (`src/`) اجرا می‌شود تا پیش‌نمایش زنده
محیط توسعه بدون خطر از کار نیفتد. انتقال فیزیکی به `apps/web` (Monorepo کامل) یک
مهاجرت ساده اما نیازمند تغییر اسکریپت‌های ریشه است و **قبل از اجرا منتظر تأیید
مالک می‌مانیم** (بخش ۷).

---

## ۲) لایه‌های نرم‌افزار

```
UI (View Components)
   │  فقط فراخوانی قراردادها — هیچ منطق تجاری
   ▼
Service / Repository Contracts   (src/services/contracts + packages/shared)
   │  UI به «قرارداد» وابسته است نه پیاده‌سازی
   ▼
Repository Implementations
   ├── فاز ۱: Unimplemented* (خطای صادقانه PhaseNotImplementedError)
   └── فاز‌های بعد: Rest*/NextAuth* (بدون تغییر UI)
```

- **اصل وابستگی معکوس:** تعویض Backend = تعویض پیاده‌سازی Repository؛ صفر بازنویسی UI.
- **خطای صادقانه:** در فاز ۱ هیچ دکمه‌ای موفقیت جعلی نشان نمی‌دهد؛ همه‌چیز وضعیت
  واقعی «فعال‌نشده در این فاز» را اعلام می‌کند.

---

## ۳) نقش‌ها و توسعه‌پذیری

- **منبع حقیقت نقش‌ها:** `packages/shared/src/roles-core.ts` (داده خالص) —
  وب و موبایل هرکدام ظاهر خودشان را روی همین داده سوار می‌کنند.
- افزودن نقش جدید (راننده وانت‌بار، شرکت حمل‌ونقل، متخصص تعمیرات) = افزودن یک
  entry + ظاهر پلتفرمی؛ بدون بازنویسی هیچ صفحه‌ای.
- نقش‌های آینده در `FUTURE_ROLES` ثبت شده‌اند ولی **هیچ UI ندارند**.
- دسته‌بندی خدمات از نقش‌ها جدا است؛ گسترش به حوزه‌های جدید و شهرهای جدید
  (فعلاً فقط تهران فعال) در تنظیمات آینده پنل مدیریت انجام می‌شود.

## ۴) پنل مدیریت مرکزی

- **جایگاه:** وب مستقل و امن در کنار وب‌سایت؛ **هرگز** داخل اپ عمومی مشتری/نصاب/فروشگاه.
- در فاز ۱ داخل همان اپ Next.js با بخش کاملاً مجزا (#/admin، چیدمان تیره مستقل)
  پیاده‌سازی شده تا در فاز Backend راحت به دامنه/سرویس جدا (مثلاً admin.example.com)
  منتقل شود.
- **RBAC:** مدل نقش‌ها و مجوزها در `packages/shared/src/admin-rbac.ts` —
  ۵ نقش مدیریتی، ۱۷ مجوز، فیلتر منو بر اساس نقش + پیام صادقانه عدم دسترسی.
- ⚠️ **اصل امنیتی:** کنترل دسترسی واقعی باید سمت سرور اجرا شود؛ مخفی‌کردن منو در
  UI فقط نمایش معماری است، نه کنترل امنیتی.
- **Audit Log:** طراحی تاریخچه Append-Only برای تغییر وضعیت سفارش‌ها و عملیات
  حساس از فاز ۱ در پنل نمونه‌سازی شده (بخش سفارش‌ها).
- مسئولیت‌های پنل (نقشه آینده): کاربران، فروشگاه‌ها، نصاب‌ها، سفارش‌ها، مالی،
  شکایات/تخلفات، آمار و گزارش‌ها، تنظیمات کل پلتفرم.

## ۵) ناوبری و مسیرها (فاز ۱)

کل تجربه وب روی مسیر «/» با ناوبری hash اجرا می‌شود (محدودیت محیط پیش‌نمایش)،
پشتیبانی کامل از دکمه بازگشت مرورگر:

| مسیر | نما |
|---|---|
| `#/` | خانه و انتخاب نقش |
| `#/login/customer` | ورود مشتری |
| `#/login/installer` | ورود نصاب + فروشگاه |
| `#/login/shop` | ورود نصاب + فروشگاه |
| `#/guide` | راهنما |
| `#/about` | درباره ما |
| `#/status` | وضعیت توسعه + ماتریس امکانات |
| `#/admin` | پنل مدیریت (ورود نمایشی) |
| `#/admin/{overview,users,shops,installers,orders,finance,violations,reports,settings}` | بخش‌های پنل |

**مهاجرت به مسیرهای واقعی Next.js (فاز بعد):** قرارداد ViewId در
`src/lib/navigation.ts` متمرکز است؛ انتقال به App Router شامل ساخت
`app/(routes)/...` و حذف لایه hash — بدون تغییر هیچ کامپوننت UI.

## ۶) وضعیت flutter_app (میراث مشخصات قبلی)

مشخصات اولیه پروژه فناوری موبایل را Flutter تعیین کرده بود و اپ Flutter
کاملی ساخته شد. دستور جدید فاز ۱، **React Native + Expo + TypeScript** را
الزامی کرده است. تصمیم ایمن:

- پوشه `flutter_app/` **دست‌نخورده و منجمد** باقی می‌ماند (هیچ حذف یا تغییری).
- توسعه موبایل به `apps/mobile` (Expo) منتقل شد.
- حذف نهایی flutter_app و CI مربوط به آن (`.github/workflows/flutter-apk.yml`)
  یک تغییر مخرب است و **فقط با تأیید مالک** در فاز بعد انجام می‌شود.

## ۷) مهاجرت‌های نیازمند تأیید مالک (ثبت‌شده، اجرانشده)

1. انتقال وب از ریشه به `apps/web` (Monorepo کامل) — خطر: تغییر اسکریپت‌های dev.
2. حذف flutter_app و flutter-apk.yml — خطر: حذف کد تست‌شده قبلی.
3. پیاده‌سازی Backend عملیاتی (NestJS؟) و انتخاب قطعی PostgreSQL.
4. انتقال پنل مدیریت به دامنه/سرویس مستقل با احراز هویت سمت سرور.

## ۸) قواعد اشتراک کد (وب ↔ موبایل)

| اشتراک | ممنوع |
|---|---|
| مدل‌های داده، نقش‌ها، RBAC | اشتراک اجباری UI وب و موبایل |
| اعتبارسنجی ورودی‌ها | یکسان‌سازی تجربه کاربری دو پلتفرم |
| نسخه/بیلد و ماتریس امکانات | — |

## ۹) امنیت در معماری

- قرارداد Repository → منطق تجاری به UI نشت نمی‌کند.
- هیچ Secret در کد/مخزن؛ `.env*` در gitignore؛ الگو: `packages/config/env.example`.
- ورودی‌ها همیشه سمت UI اعتبارسنجی می‌شوند (فاز ۱) و سمت سرور دوباره (فاز Backend).
- عملیات حساس پنل مدیریت: ثبت سوابق، مسئول مشخص، زمان دقیق — طراحی از فاز ۱.
