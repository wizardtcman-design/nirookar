# نقشه راه توسعه — الزامات آینده ثبت‌شده

> این موارد طبق دستور مالک از همین ابتدا در معماری لحاظ شده‌اند؛ پیاده‌سازی
> هر یک نیازمند تأیید جداگانه است.

## ۰) قوانین تجاری قطعی (دستور مالک — فاز ۲ گام ۱)

- **قانون «صفر درصد هاردکد»:** هیچ عدد مالی/زمانی در کد نیست؛ همه از
  `PlatformSettings` (packages/shared/platform-settings.ts) خوانده و از پنل
  ادمین به‌صورت زنده ویرایش می‌شود.
- **اولویت نصاب وابسته به فروشگاه: ۲ ساعت** (قانون ۲۴ ساعت قبلی به‌طور رسمی حذف شد).
- **بازدید حضوری رایگان ممنوع (ضد تبانی):** بازدید حضوری فقط با بیعانه امانی؛
  در صورت ثبت سفارش، بیعانه از فاکتور کسر می‌شود؛ در صورت لغو برای کار خارج
  از اپ، بیعانه سوخته و بین پلتفرم و نصاب تقسیم می‌شود.
- **ضمانت نصاب:** مراجعه حضوری + قرارداد فیزیکی + سفته — ثبت با تیک
  «تأیید قرارداد و دریافت سفته حضوری» در پنل ادمین + Audit Log.
- **خرید اقساطی (BNPL):** برچسب «۴ قسط بدون چک و ضامن» — قابل خاموش/روشن از ادمین.
- **پلیس خودکار چت:** سانسور شماره موبایل (ارقام/فاصله/حروف فارسی) و آیدی
  شبکه‌های اجتماعی در چت و توضیحات سفارش تا قبل از پرداخت امانی.

## ۱) پیگیری زنده سفارش (فاز ۲ — گام بعدی)

مشتری مراحل سفارش را مرحله‌به‌مرحله می‌بیند. هر تغییر وضعیت شامل:

- وضعیت قبلی → وضعیت جدید
- شخص انجام‌دهنده تغییر + نقش او
- تاریخ و ساعت دقیق
- توضیحات
- امکان پیوست عکس/ویدئو در صورت نیاز

**طراحی فنی:** تاریخچه Append-Only سمت سرور (قابل دستکاری نیست)؛ نمونه UI این
طراحی در پنل مدیریت فاز ۱ (بخش سفارش‌ها → تاریخچه) پیاده شده است.

## ۲) رسیدگی به خسارت مشتری (فاز ۳)

اگر فروشگاه یا نصاب به مشتری خسارت وارد کند، سازوکار مشخص رسیدگی و جبران وجود دارد
و **اولویت با رسیدگی منفقانه و جبران خسارت مشتری است**.

مواردی که باید طراحی و بررسی شوند (هیچ‌کدام بدون تأیید مالک قطعی نمی‌شود):

- ثبت و مستندسازی شکایت + مدارک و شواهد
- بررسی مسئولیت طرفین بر اساس قراردادها و تعهدات
- سازوکار جبران خسارت و ضمانت اجرای متناسب (جریمه/محدودیت)
- امکان استفاده از بیمه یا ضمانت معتبر
- بررسی الزامات قانونی و حقوقی

ℹ️ ضمانت فنی همکاری نصاب در فاز ۱ عملیاتی = مراجعه حضوری، قرارداد فیزیکی و
سفته (بخش ۰ همین سند) — سازوکار جبران خسارت مشتری همچنان نیازمند طراحی حقوقی
و تأیید مالک است.

## ۳) درآمدزایی (فاز ۳ — جایگاه معماری آماده است)

مدل‌های درآمدی که ساختار آینده باید مدیریت کند:

- کمیسیون سفارش
- اشتراک ماهانه
- خدمات ویژه
- فروش محصولات
- سایر مدل‌های قابل بررسی

در فاز ۱ فقط جایگاه معماری (ماژول finance در `apps/api` + بخش مالی پنل) مشخص شده است.

## ۴) گسترش جغرافیایی و نقش‌ها

- پلتفرم به هیچ شهری هاردکد نیست؛ شهرهای فعال از **تنظیمات پنل مدیریت**
  تعریف می‌شود (فاز ۲ گام ۱ پیاده‌سازی شد) و ثبت‌نام فقط در شهرهای فعال باز است.
- نقش‌های آینده ثبت‌شده: راننده وانت‌بار، شرکت حمل‌ونقل، متخصص تعمیرات —
  افزودن هر نقش فقط یک entry در `packages/shared/src/roles-core.ts` است.

## ۵) مهاجرت‌های فنی — تکلیف تعیین‌شده (تصمیم مالک، فاز ۲ گام ۱)

| مهاجرت | تصمیم | وضعیت |
|---|---|---|
| حذف flutter_app + flutter-apk.yml | تأیید شد | **اجرا شد** ✅ |
| انتقال وب به apps/web | تغییر نکند (سلامت پیش‌نمایش زنده) | بسته شد ⚠️ |
| Backend عملیاتی (API Routes + SQLite) | تأیید شد — گام ۱ | **اجرا شد** ✅ — تعویض آینده به PostgreSQL فقط با تغییر datasource |
| پنل مدیریت → دامنه/سرویس مستقل | آینده | منتظر استقرار عملیاتی |
| ناوبری hash → مسیرهای واقعی Next.js | آینده | قرارداد ViewId متمرکز است |
| اپ موبایل → اتصال به API ورود/ثبت‌نام | گام بعدی فاز ۲ | پس از استقرار endpoint عمومی |
