## ۲) سه محصول و وضعیت واقعی هرکدام

### الف) وب‌سایت — ✅ فعال و در حال اجرا
- **تکنولوژی:** Next.js 16.1.3 (App Router + Turbopack) + React 19 + TypeScript 5 (strict) + Tailwind CSS 4 + shadcn/ui + framer-motion
- صفحه اصلی واکنش‌گرا (موبایل/تبلت/دسکتاپ) با **۳ ورودی کاملاً متمایز رنگی**: مشتری (سبزآبی)، نصاب (سرمه‌ای)، فروشگاه (مرجانی)
- فرم‌های ورود سه نقش با **اعتبارسنجی واقعی سمت کاربر**: موبایل `09xxxxxxxxx`، ایمیل، رمز ≥۶، نرمال‌سازی ارقام فارسی/عربی
- ناوبری hash با پشتیبانی کامل دکمه بازگشت مرورگر: `#/` · `#/login/customer` · `#/login/installer` · `#/login/shop` · `#/guide` · `#/about` · `#/status` · `#/admin`
- ناوبری بالایی در دسکتاپ، نوار پایین شناور در موبایل
- صفحه وضعیت توسعه (`#/status`) با **ماتریس امکانات زنده** از `packages/shared`
- لایه Repository با قرارداد `AuthRepository` و پیاده‌سازی `Unimplemented` با خطای صادقانه `PhaseNotImplementedError` (هیچ دکمه‌ای موفقیت جعلی نشان نمی‌دهد)

### ب) پنل مدیریت مرکزی — ✅ ساختار و طراحی کامل (غیرعملیاتی طبق دستور)
- داخل همان اپ Next.js با بخش **کاملاً مجزا و چیدمان تیره مستقل**: `#/admin`
- ورود نمایشی با انتخاب نقش (۵ نقش مدیریتی) — فیلدهای نام کاربری/رمز عمداً غیرفعال
- **۹ منو:** داشبورد، کاربران، فروشگاه‌ها، نصاب‌ها، سفارش‌ها، مالی، تخلفات/شکایات، گزارش‌ها، تنظیمات
- **RBAC واقعی** از `packages/shared/src/admin-rbac.ts`: ۵ نقش × ۱۷ مجوز، فیلتر منو بر اساس نقش + پیام صادقانه «دسترسی مجاز نیست» برای دسترسی مستقیم غیرمجاز
- **نمونه Audit Log سفارش** (تاریخچه Append-Only: وضعیت قبل→بعد، شخص، زمان، مستندات) — طراحی برای فاز ۲
- همه داده‌ها ۱۰۰٪ نمایشی با برچسب «داده نمایشی» (`src/lib/admin-demo-data.ts`)
- ⚠️ اصل امنیتی ثبت‌شده: کنترل دسترسی واقعی باید سمت سرور باشد؛ مخفی‌کردن منو در UI فقط نمایش معماری است

### ج) اپ موبایل — ⚠️ کد کامل، نیاز به Build
- **تکنولوژی:** Expo SDK 53 + React Native 0.79 + TypeScript + expo-router
- ۶ فایل مسیر: `index` (انتخاب نقش)، `customer`، `professional`، `guide`، `about` + `_layout`
- RTL با I18nManager؛ داده نقش‌ها/اعتبارسنجی/نسخه از `packages/shared` (اشتراک واقعی کد با وب)
- `eas.json` + سه راه ساخت APK مستندشده (GitHub Actions / محلی gradlew / EAS)
- **تاکنون Build نشده** — محیط ابری فاقد SDK اندروید است؛ ساخت APK به CI (GitHub Actions) موکول شده و تایپ آن در CI بررسی می‌شود

## ۴) ⛔ قواعد طلایی غیرقابل‌نقض (از دستور مالک — هر هوش مصنوعی ادامه‌دهنده موظف است)

1. **بدون تأیید جداگانه مالک ممنوع است:** Backend واقعی، ثبت‌نام/ورود واقعی، پرداخت، دریافت پول، کمیسیون عملیاتی، سفارش واقعی، پیامک واقعی، سرویس خارجی، ذخیره داده واقعی کاربر، سیستم مالی واقعی، رسیدگی عملیاتی به شکایت.
2. **دکمه مرده ممنوع:** هر دکمه/فرم/مسیرِ در محدوده فاز باید رفتار واقعی و روشن داشته باشد. قابلیتِ هنوز فعال‌نشده باید **صادقانه وضعیتش را اعلام کند** و هرگز موفقیت جعلی نشان ندهد.
3. **برچسب Demo:** داده نمایشی همیشه باید با برچسب مشخص از داده واقعی تفکیک شود.
4. **نسخه‌بندی:** نسخه محصول فعلی `0.1.0` — شماره `1.0.0` فقط برای اولین انتشار عمومی رسمی رزرو است. بیلد مستقل از نسخه و افزایشی: `001، 002، 003…`. versionCode اندروید فقط افزایشی. انتشار نسخه آزمایشی به‌عنوان Release عمومی ممنوع.
5. **امنیت:** هیچ Secret/توکن/رمزی در کد یا مخزن. توکن GitHub فقط در GitHub Secrets و هرگز در خروجی چاپ نشود. `.env*` در gitignore.
6. **بدون حذف کار سالم:** `flutter_app/` و `flutter-apk.yml` دست‌نخورده تا تأیید حذف. تغییر مخرب/معماری بدون گزارش (دلیل/ریسک/هزینه/برنامه) و تأیید مالک ممنوع.
7. **ماتریس امکانات:** هر قابلیت جدید باید در `packages/shared/src/feature-matrix.ts` + `docs/FEATURE_PARITY_MATRIX.md` ثبت شود (اپ/وب/فاز/وضعیت/نیاز Backend). قاعده طلایی: قابلیتی که در یکی ساخته می‌شود باید در دیگری ساخته شود یا با دلیل مستند «عمداً خارج» اعلام شود.
8. **معماری لایه‌ای:** UI فقط به «قرارداد Repository» وابسته است؛ تعویض Backend آینده = تعویض پیاده‌سازی Repository بدون بازنویسی UI.
9. **گزارش صادقانه:** گزارش فقط بر اساس «چه چیزی واقعاً ساخته و تست شد»، نه برنامه‌ها. ادعای «غیرقابل‌نفوذ بودن» ممنوع؛ ریسک‌ها و محدودیت‌ها باید شفاف اعلام شوند.

## ۵-۲) قوانین تجاری جدید ثبت‌شده (دستور مالک — غیرقابل‌نقض)

1. **قانون «صفر درصد هاردکد»:** همه اعداد مالی/زمانی از `PlatformSettings` (packages/shared) خوانده می‌شوند و از پنل ادمین قابل ویرایش زنده است — مدل درآمد نصاب (درصدی ۱۵٪/ثابت/اشتراک)، سهم فروشگاه معرف (۵٪ از کارمزد پلتفرم)، مدل غرفه (رایگان/اشتراک/درصد فروش)، گارانتی هر دسته شغلی، اولویت نصاب وابسته (**۲ ساعت** — قانون ۲۴ ساعت قبلی حذف شد)، مهلت تأیید مشتری و تسویه (۲۴ ساعت).
2. **سه روش قیمت‌گذاری + قفل بیعانه (ضد تبانی):** ① محاسبه هوشمند متراژ/تعداد ② بازدید تصویری رایگان (ویدئو ≤۱۵ ثانیه؛ شماره و آدرس تا قبل از پرداخت قفل) ③ بازدید حضوری با بیعانه اجباری امانی (قابل تنظیم ۵۰۰هزار تا ۱میلیون) — اگر سفارش اصلی ثبت شود بیعانه از فاکتور کسر می‌شود؛ اگر طرفین برای کار خارج از اپ لغو کنند، بیعانه سوخته و بین پلتفرم و نصاب تقسیم می‌شود.
3. **ضمانت نصاب:** مراجعه حضوری + قرارداد فیزیکی + سفته؛ تیک «تأیید قرارداد و دریافت سفته حضوری» در پنل ادمین (پیاده‌سازی شد).
4. **قفل کد ملی:** الگوریتم ریاضی صحت‌سنجی + جلوگیری از ثبت تکراری + هشدار ادمین (پیاده‌سازی شد)؛ آدرس سکونت نصاب محرمانه فقط برای ادمین.
5. **BNPL:** برچسب «۴ قسط بدون چک و ضامن» با محاسبه خودکار — قابل خاموش/روشن از ادمین.
6. **پلیس خودکار چت:** سانسور شماره موبایل و آیدی شبکه‌های اجتماعی در چت و توضیحات سفارش تا قبل از پرداخت امانی (قاعده در تنظیمات ثبت شد؛ اجرای زنده با ساخت چت).

## ۶) معماری‌های آینده که از الان پیش‌بینی شده‌اند

1. **پیگیری زنده سفارش (فاز ۲):** تاریخچه Append-Only سمت سرور — هر تغییر وضعیت شامل وضعیت قبل/بعد، انجام‌دهنده + نقش، زمان دقیق، توضیح، پیوست عکس/ویدئو. بدون امکان دستکاری بدون‌ردپا. نمونه UI در پنل فاز ۱ هست.
2. **ضمانت واقعی نصاب (مدل رسمی فاز ۱ — جایگزین متن قبلی):** مراجعه حضوری نصاب به انبار/دفتر مرکزی + امضای قرارداد فیزیکی + تحویل سفته ضمانت؛ وضعیت در پنل مدیریت با تیک **«تأیید قرارداد و دریافت سفته حضوری»** توسط مدیر ثبت و در Audit Log ثبت می‌شود. (این بند جایگزین عبارت قبلی «چک و سفته تضمین کافی نیست» است.)
3. **درآمدزایی (فاز ۳):** کمیسیون سفارش، اشتراک ماهانه، خدمات ویژه، فروش محصول — همه اعداد از `PlatformSettings` خوانده می‌شود (هیچ عددی هاردکد نیست).
4. **توسعه‌پذیری:** شهر جدید و نقش‌های آینده (وانت‌بار، حمل‌ونقل، تعمیرات) = افزودن entry در `roles-core.ts` + تعریف شهر از پنل؛ بدون بازنویسی UI.
